# GoFlow V3 本地智能体工作流平台使用与实践白皮书

版本：V3

发布日期：2026-08-17

产品类型：本地智能体工作流平台

当前产品支持范围：Windows 10/11 x64 的 PC Web 平台；兼容源码与历史 Linux 证据不是发布要求。

本机日常操作、故障排查及数据清理见[本机操作与维护](./local-operations.zh-CN.md)。历史设计和验收记录不替代当前任务的实际产出验收。

## 摘要

GoFlow V3 是一个面向普通用户和工程团队的本地智能体工作流平台。它把自然语言任务、真实文件、受控工具、可恢复状态和质量验证连接成一个完整交付闭环。用户不需要先理解智能体拓扑、模型路由、沙箱参数或复杂节点图，只需要选择工作区、描述目标、提供必要的截图或文件，然后在任务上下文中处理审批并检查交付证据。

平台的“本地”指运行时编排、工作区状态、任务副本、密钥引用、工具代理和交付审计在本机完成；模型服务可以使用用户配置的兼容 Provider。GoFlow 不把模型输出当成完成证明，任务只有在真实文件、Diff、构建、测试、静态检查、来源证据、文档校验或运行健康检查满足要求后，才允许进入交付阶段。

V3 的核心取舍是：普通任务优先直接完成，复杂任务才进入工作流；页面优先但不牺牲工程能力；资源数量有限但内置资源可组合；确定性代码负责边界和验证，模型负责理解、决策和生成候选结果；未知代码和第三方 MCP 必须经过操作系统原生受控执行。

关键词：本地智能体、工作流、原生沙箱、MCP、Skill、工程化交付、质量门、任务恢复、文档自动化

## 1. 文档定位

本白皮书不是营销承诺，也不是单个页面的按钮说明。它是 GoFlow V3 的产品使用、架构理解、任务设计和验收基线，回答以下问题：

1. GoFlow 解决什么问题，明确不解决什么问题。
2. 用户、智能体、工作流、Skill、连接和工具如何协作。
3. 一个任务从输入到交付经过哪些状态和安全边界。
4. 开发、网安、运维、资料核验和 Office/WPS 文档任务怎样获得可复核产物。
5. 如何判断任务“真的完成”，以及失败后如何恢复。

普通用户按第 6 章和附录 A 操作即可；需要设计团队流程、导入外部资源或制定验收规范的用户，还应阅读第 5、7、8、9 和 10 章。

## 2. 产品定义与边界

### 2.1 产品定义

GoFlow V3 由四个部分组成：

| 部分 | 定义 | 用户看到的结果 |
| --- | --- | --- |
| 任务工作台 | 任务输入、附件、运行状态、审批和产物入口 | 一次任务从提出到交付的主页面 |
| 智能体运行时 | 需求理解、路由、上下文检索、工具调用和结果整合 | 系统自动选择合适能力 |
| 工作流编排器 | 阶段、分支、并行、检查点、恢复和质量门 | 可复用、可审计的复杂流程 |
| 受控执行层 | 工作区、MCP、命令、主机和远程操作的边界 | 不越权、不静默降级的工具执行 |

### 2.2 解决的问题

- 把“我要完成一件工程工作”转化为可执行的任务契约，而不是只返回聊天文本。
- 让普通用户通过页面使用开发、网安、运维、资料和文档能力，不必先掌握命令行和配置文件。
- 让复杂任务拥有阶段状态、审批、检查点、重启恢复和质量门，避免从头重复执行。
- 让第三方工具和外部资源可以兼容，但不能绕过工作区和安全边界。
- 让文档修改、代码修改和运维变更都能留下真实产物和证据。

### 2.3 明确不做的事情

- 不把 Docker、Podman 或虚拟机作为产品运行时依赖。
- 不提供无限制的桌面控制或模拟点击一切应用的能力。
- 不要求普通用户配置模型拓扑、Token 预算、底层挂载和系统隔离参数。
- 不用模型自评、模拟测试或“看起来完成”替代真实文件和验证。
- 不把公网多租户、复杂组织权限和社交机器人作为 V3 的核心范围。

## 3. 设计原则

### 3.1 任务优先

资源是实现任务的手段，不是用户的起点。普通用户进入“任务”页面即可开始工作；资源页和工作流页用于复用、治理和专业设计。

### 3.2 结果优先

页面默认突出当前状态、下一步、审批、结论和产物。工具参数、内部事件、上下文成本和完整日志按需展开，避免多层面板和重复滚动。

### 3.3 能力内置，配置从简

平台内部可以使用路由、子智能体、并行和质量门，但普通用户不需要手工编排这些细节。用户能配置的资源包括智能体、子智能体、工作流、Skill、单个 MCP 工具和 MCP 连接六类。

### 3.4 确定性边界优先

模型可以理解自然语言、识别意图和提出修改；代码负责路径、权限、审批、状态、超时、重试、哈希、Diff 和验收判定。模型不能直接把阶段标记为成功，也不能绕过工具代理写入系统。

### 3.5 证据驱动交付

任务交付必须能回答“改了什么、怎么证明、失败如何恢复”。没有证据的自然语言结论只能作为草稿，不能作为完成状态。

## 4. 用户与系统模型

### 4.1 一个任务的完整链路

```mermaid
flowchart LR
    A[用户目标与附件] --> B[需求编译]
    B --> C[任务路由]
    C --> D[上下文检索与去重]
    D --> E[持久化执行状态机]
    E --> F[工具代理与原生边界]
    F --> G[检查点、审批、恢复]
    G --> H[质量门与交付清单]
    H --> I[下载、写回或恢复]
```

### 4.2 任务契约

每次运行内部都会形成一份精简任务契约，至少包含：

- 目标：要解决的实际问题。
- 范围：允许读取、修改或访问的对象。
- 交付物：文件、Diff、报告、数据、PDF 或运行结果。
- 验收条件：测试、构建、引用、格式、健康检查或人工确认。
- 授权与风险：网络、命令、主机、远程和破坏性动作的边界。
- 恢复要求：检查点、备份、回滚或失败后的重试范围。

用户不必手工填写所有字段，但越是复杂的任务，越应该在请求中明确它们。

### 4.3 简单任务与复杂任务

| 场景 | 默认路径 | 用户动作 |
| --- | --- | --- |
| 单文件读取、解释、轻量修改 | 直接任务 | 输入目标，检查结果 |
| 代码修复和测试 | 直接任务或短工作流 | 指定范围和验收命令 |
| 多阶段开发交付 | 工作流 | 确认计划、审批高风险阶段 |
| 授权安全审查 | 安全工作流 | 提供范围、审批主动动作 |
| 周期报告或固定运维流程 | 可复用工作流 | 维护模板和质量门 |

## 5. 资源体系与兼容模型

### 5.1 六类用户资源

| 资源 | 职责 | 设计约束 |
| --- | --- | --- |
| 智能体 | 领域角色、判断和交付风格 | 角色稳定，不能把所有逻辑塞进提示词 |
| 子智能体 | 边界明确的独立子任务 | 必须有输入、输出和停止条件 |
| 工作流 | 阶段顺序、路由、审批和恢复 | 复杂才使用，避免无意义节点 |
| Skill | 方法、参考、脚本和验收规则 | 兼容 `SKILL.md`，脚本仍受工具策略约束 |
| MCP 工具 | 可由智能体调用的单个结构化能力 | Schema、参数、结果和产物引用必须可追溯 |
| 连接 | MCP 或外部能力入口 | 标准 stdio 协议，原生受控执行 |

Kit 是资源组合包，不新增用户资源类型。普通用户优先使用内置 Kit 和模板，专业用户可以将其实体化为上述资源。

### 5.2 外部资源兼容

平台兼容常见 `SKILL.md`、`AGENTS.md`、`CLAUDE.md` 和标准 MCP。兼容的含义是读取和映射可理解的结构，不是无条件接受外部权限。无法无损支持的字段必须给出提示；任何资源都不能绕过工作区、审批、审计和质量门。

### 5.3 中文化与配置原则

普通用户可见的资源名称和说明使用中文。连接编辑器只显示用途、命令、启用状态和必要参数；模型 Key 在设置页单独管理；AppContainer、ACL、Landlock、seccomp、namespace、cgroup 和 Token 等底层细节不进入普通配置表单。

## 6. 标准使用方法

### 6.1 安装和初始化

1. 下载 Windows x64 发布包。
2. 校验 `SHA256SUMS` 和发布签名。
3. 解压到用户可写的应用目录。
4. 启动 `run-goflow.cmd`。
5. 在浏览器打开 `/console`。
6. 在“设置”中填写模型服务 API Key。
7. 选择工作区并运行一个只读任务。

实际模型和推理强度以设置页当前模型服务配置为准。如果服务返回模型错误，应核对接口地址、支持的模型名称和 Key 是否匹配，并执行连接测试。

### 6.2 任务输入规范

推荐使用五段式请求：

```text
目标：要完成什么。
范围：允许读取或修改哪些目录、文件、主机或网址。
交付：需要哪些文件、报告、数据或说明。
验收：必须运行哪些测试、检查或复测。
限制：哪些动作必须审批，哪些对象绝不能触碰。
```

输入框支持粘贴截图、拖入文件、选择附件和 `@相对路径` 引用。附件会保存哈希并绑定任务；视觉 Provider 不可用时平台会明确拒绝或提示，不会伪造识图结果。

### 6.3 审批和人工输入

只读检查通常可以直接执行。写文件、执行命令、网络访问、主机配置和远程操作可能触发审批。审批显示在当前任务或工作流中，包含目标、范围、原因和作用域。批准只对当前运行和显示的作用域生效，不会变成全局权限。

### 6.4 产物与写回

任务完成后先检查：

1. 文件或文档是否真实存在。
2. Diff 是否只包含预期变化。
3. 构建、测试、静态检查或格式校验是否真实执行。
4. 报告、来源、日志或健康检查是否可以回放。
5. 风险、未完成项和恢复编号是否完整。

通过质量门后，可以下载产物或应用已验证变更。写回前会检查外部并发修改，写回后保留恢复记录；放弃任务只清理任务副本，不修改真实工作区。

### 6.5 任务恢复

任务状态和工作流运行会持久化。页面关闭、服务重启或审批等待不会自动丢失任务。恢复时优先从最近检查点继续，不重复已经有证据的阶段。若真实工作区已被外部修改，应先重新确认 Diff，再决定继续、重试或恢复。

## 7. 五类领域实践

### 7.1 开发编码

标准闭环为：代码库地图、需求定位、最小修改、构建、测试、静态检查、Diff 审查和交付说明。

建议交付：源码、测试结果、构建命令、Diff、运行说明、风险和恢复方式。

### 7.2 网络安全

标准闭环为：授权确认、范围收集、被动检查、证据记录、风险判断、修复建议、复测和报告。主动扫描、外部访问和可能造成副作用的动作必须限界并审批。外部内容和工具结果都按不可信数据处理。

建议交付：授权范围、时间窗口、发现、原始证据、风险等级、修复/缓解、复测结果和正式报告。

### 7.3 网络运维

标准闭环为：只读事实、影响分析、备份、变更计划、干跑、审批、执行、健康检查和回滚验证。本机配置和 SSH 远程目标必须显式选择，不能把未知主机当作默认目标。

建议交付：诊断证据、变更前后状态、命令或配置 Diff、备份位置、健康检查和恢复命令。

### 7.4 互联网资料核验

标准闭环为：检索、来源去重、原文摘录、发布时间和访问时间记录、冲突识别、结论映射和多格式交付。

建议交付：带引用的 Markdown、结构化 JSON、可复用 CSV、来源列表、冲突项和无法确认的内容。

### 7.5 Office/WPS 文档

文档能力覆盖：读取现有文件、新建、基于模板修改、按意思准确修改、保留格式精确修改、合并、结构校验和导出 PDF。开发、网安、运维和资料任务可以复用同一文档能力生成需求文档、报告、运行手册和证据包。

建议交付：可编辑源文件、预览或 PDF、结构校验结果、格式保留说明和修改前后差异。

## 8. 工作流设计与治理

### 8.1 使用条件

只有在任务具有固定阶段、多个角色交接、分支/并行、人工审批、检查点或重复执行价值时，才应设计工作流。一次性小任务直接运行更快，也更容易定位问题。

### 8.2 最小工作流

```text
开始 -> 分析 -> 实现/处理 -> 验证 -> 质量门 -> 交付 -> 结束
```

执行节点初始只填写：执行者、Skill、输入、输出和下一步。需要时再增加条件、循环、重试、审批、产物和验收条件。

### 8.3 工作流验收

- 必须有开始和结束节点。
- 每个阶段都有明确输入和输出。
- 分支有默认路径或失败路径。
- 高风险阶段有审批边界。
- 交付阶段有文件、Diff、测试、证据或文档校验。
- 失败能够重试有限次数或进入明确修复路径。
- 运行后能够从检查点恢复。

禁止为了增加“智能感”创建没有独立产物的子智能体讨论、重复读取和无产物模型调用。

## 9. 原生安全模型

### 9.1 平台边界

GoFlow 不依赖 Docker、Podman 或虚拟机。Windows 根据能力使用 AppContainer、受限令牌、ACL 和 Job Object；Linux 使用 Landlock、user/mount/network namespace、seccomp、rlimit 和 cgroup v2。平台会先探测宿主能力，再决定是否允许未知代码运行。

### 9.2 工作区和任务副本

未知代码和第三方 MCP 进入独立任务副本；依赖通过内容寻址缓存以只读方式暴露；真实工作区写回必须经过工具代理、Diff 检查、审批和质量门。工具不能通过路径、符号链接或环境变量逃逸到工作区外。

### 9.3 网络和凭据

任务进程默认无网络。联网需求通过受控工具和明确权限完成。API Key、SSH 私钥和敏感环境变量只使用本地引用，不写入资源文件、日志、报告、任务产物或版本库。

### 9.4 失败时的拒绝优先

如果强沙箱能力不完整，未知代码和不可信第三方 MCP 会显示中文拒绝原因。平台不会为了让任务“看起来成功”而静默降级到不受控进程。

## 10. 工程化质量模型

### 10.1 完成判定

模型输出不是完成证明。不同领域的硬证据如下：

| 领域 | 最低交付证据 |
| --- | --- |
| 开发 | 真实 Diff、构建、测试、静态检查和运行说明 |
| 网安 | 授权范围、发现证据、风险、修复/缓解、复测和报告 |
| 运维 | 目标、诊断、变更记录、健康检查和恢复方案 |
| 资料 | 来源、引用映射、冲突、时间信息和结构化导出 |
| 文档 | 可编辑源文件、预览/PDF、结构和格式校验 |

### 10.2 质量门

质量门由确定性代码判定，包括文件存在性、哈希、Diff、命令退出码、测试结果、静态检查、来源字段、文档结构和审批状态。模型可以提出候选结果，但不能伪造通过状态。

### 10.3 效率指标

平台重点观察：每个通过交付所需的模型调用、重复上下文比例、无产物调用比例、确定性缓存命中率、工具响应耗时和恢复后重复执行量。降低 Token 不能以跳过验证或隐藏失败为代价。

## 11. 页面与交互模型

### 11.1 任务页

任务页是单列主工作区，默认显示输入、状态、当前动作摘要、审批、结果和产物。最近任务、完整运行详情和恢复记录按需打开，避免常驻多层卡片和嵌套滚动。

### 11.2 工作流页

工作流页以画布为主，工具栏保持单行。节点库和节点设置按需打开；保存、校验、运行、导入、导出和删除均有明确状态反馈。专注模式隐藏非必要侧栏，但不隐藏顶部操作和画布上下文。

### 11.3 资源与设置页

资源页管理六类资源，并允许把单个 MCP 工具直接加入工作流。设置页只保留模型 Key、工作区、外观和数据维护；高级运行边界由系统管理，不让普通用户承担底层配置成本。

## 12. 部署、升级和数据管理

### 12.1 数据分层

- Runtime home：二进制、配置、内置资源和文档。
- Workspace root：用户项目或文档目录。
- Data root：会话、密钥引用、任务记录、备份和恢复数据。
- Task staging：单次任务的暂存副本、依赖和产物。

这四类目录不能混为一谈。升级替换 Runtime home 时，Data root 和 Workspace root 应保持不变。

### 12.2 升级生命周期

正式流程为：校验归档 -> 停止旧服务 -> 安装或升级 -> 启动检查 -> 数据保留验证 -> 失败时回滚。安装器提供升级备份、回滚、保留数据卸载、重装和清除数据选项。

### 12.3 卸载原则

卸载应用不等于删除用户数据。确认不再需要会话、密钥引用、备份和恢复记录后，才使用清除数据选项。

## 13. 典型落地场景

### 场景一：截图驱动的开发修复

用户粘贴 CI 或浏览器错误截图，指定仓库和验收命令。系统识别错误上下文，检索对应文件，生成最小修改，运行测试和静态检查，最后交付 Diff 和运行说明。

### 场景二：授权 Web 安全报告

用户提供测试站点、授权范围和时间窗。系统先做被动采集，再根据审批执行有限检查，保存请求/响应证据，生成风险报告，修复后再复测并更新报告。

### 场景三：网络服务变更

用户要求调整服务配置。系统先读取事实和依赖，生成变更计划和备份方案，等待审批后执行，运行健康检查，失败时从备份恢复并提供前后状态 Diff。

### 场景四：资料核验包

用户给出主题、截止日期和来源要求。系统去重来源、记录原文和时间、标记冲突，交付带引用 Markdown、JSON 和 CSV，未确认内容单独列出。

### 场景五：模板化正式文档

用户提供 DOCX 模板、修改意图和附件。系统读取模板结构，保留样式精确替换内容，合并表格或证据，导出 DOCX/PDF，执行页数、标题、表格和可打开性校验。

## 14. 限制与风险披露

- Provider 的模型能力、视觉支持、速率限制和费用由 Provider 决定；平台会探测并提示，不会伪造能力。
- 原生沙箱能力依赖操作系统、内核、策略和用户委派权限。能力不足时未知代码会被拒绝。
- Office/WPS 精确格式操作依赖输入文件结构和可用的本机文档运行环境；每次交付都必须查看预览和校验结果。
- 网络安全和远程运维能力不替代授权、变更管理和人工复核。
- 互联网资料可能变化、下线或存在冲突，报告必须保留访问时间和原始来源。
- 模型会犯错；真实工具结果、测试和质量门是最终判断依据。
