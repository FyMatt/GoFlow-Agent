# 提示缓存命中率优化方案（v1）

> 目标：在不降低交付质量的前提下，提高供应商输入缓存命中率，降低单任务成本。
> 依据：论文 4.2.1「稳定部分与动态部分分别组织……为供应商支持的输入缓存创造条件」。
> 执行窗口：**谷时段**（工作日 18:00 之后、次日 09:00 之前，或周末全天）——官方峰时价格是谷时的 2 倍。

## 1. 基线（2026-11-05 实测）

| 指标 | 当前值 | 来源 |
| --- | --- | --- |
| 缓存命中率 | 72–75%（运维 19–22 次调用） | 20261105-153237 / 163847 |
| 单任务成本（运维） | 0.08–0.10 元（谷时等效） | 同上 |
| 单任务成本（开发） | 0.25 元（谷时等效） | 20261105-160231 |
| 未命中构成 | 冷启动约 20k + 阶段内断点约 15k + 末轮新增 | 20261105-153237 分阶段统计 |
| 阶段数 | 每轮 5–8 个，每阶段独立会话 | complex-project-delivery 模板 |

## 2. 为什么现状只能到 75%

供应商缓存是**前缀缓存**：请求从第 0 字节起最长公共前缀才命中。当前每次阶段切换都会重建：

1. 系统提示按 `agent + skill` 重建 → 不同；
2. 工具目录按阶段策略过滤 → 不同（工具定义位于请求头部）；
3. 会话历史不跨阶段传递 → 每阶段从零开始。

因此每个阶段第一次调用必然全额未命中（约 4–5k），这是当前未命中的主要来源。

## 3. 分三阶段实施

### 阶段一：稳定前缀（低风险，预期 +8~10 个点）

**改动**
- 新增工作流级系统提示构造：基座策略 + 工作流允许的**工具目录并集** + 固定契约，**跨阶段逐字节一致**；
- 把「角色说明、技能正文、阶段契约」从系统提示移入该阶段的第一条用户消息；
- 工具目录改为「工作流并集」，阶段级限制改由策略层拒绝（拒绝时返回明确原因，不静默过滤）。

**依据**：论文 4.2.1 要求「角色说明、工具定义和固定契约保持可重复的顺序」。

**预期**：系统前缀（约 1.8k）跨阶段命中；冷启动从 4–5k 降到 2–3k；命中率 72% → 80% 左右；单任务成本 −8~10%。

**风险**：模型看到本阶段不可用的工具 → 可能误调用。缓解：用户消息里明确本阶段允许的工具；策略拒绝返回可读原因。

### 阶段二：跨阶段消息复用（中风险，预期再 +6~8 个点）

**改动**
- `schema.AgentResult` 增加 `Messages []schema.Message`（`json:"-"`，不落盘、不进报告）；
- 工作流运行器保存本运行的消息序列，下一阶段以 `InitialMessages` 注入并追加本阶段输入；
- 续跑（continuation）沿用同一序列，不再从空会话开始；
- 沿用已有的原地裁剪（保留最近 24 条），控制上下文规模。

**预期**：历史前缀跨阶段命中；命中率 80% → 85~88%；单任务成本再 −10~15%。

**风险**：阶段隔离语义变化；工具调用与结果顺序需保持协议合法（已有 `SanitizeToolMessages` 兜底）。缓解：阶段边界插入一条固定的分隔消息；恢复逻辑仍以检查点为准。

### 阶段三：裁剪与冷启动收敛（低风险，预期 +2~4 个点）

**改动**
- 阶段输入改为「摘要 + 产物引用」，完整计划按需读取；
- 单分片预算与批量编辑继续生效，减少因返修带来的新会话。


## 4. 探针实测与阶段一结论（2026-11-09）

用最小请求直接测供应商缓存行为（成本约 0.01 元）：

| 实验 | 输入 token | 命中 | 说明 |
| --- | --- | --- | --- |
| 首次调用 | 746 | 0 | 冷启动 |
| 同 system、同 tools、换问题 | 747 | 512（68%） | 正常命中 |
| 同 system、换 tools | 758 | 512（67%） | 工具定义不破坏缓存 |
| system 前缀相同、尾部不同 | 749 | 256（34%） | 缓存按 256 token 块对齐 |

**阶段一（稳定前缀重排）实测失败，已回滚**：

| 指标 | 基线 | 阶段一 | 结论 |
| --- | --- | --- | --- |
| 运维调用数 | 19–22 | 31 | +40%，退化 |
| 运维缓存命中 | 72–75% | 73% | 无提升 |
| 运维成本（谷时） | 0.08–0.10 元 | 0.159 元 | 变贵 |
| 开发调用数 | 31–55 | 141 | 打转 |

原因分析：系统提示只有约 1.8k token，而阶段冷启动的大头是**该阶段的用户输入**（计划、阶段契约），那部分是每个阶段独有的，重排系统提示无法共享它。因此阶段一没有收益，按计划停止条件回滚。

**后续结论**：在这套「每阶段独立会话」的架构下，缓存命中已接近上限（72–75%）；继续提升必须做跨阶段消息复用（阶段二），但它需要改动消息传递、阶段隔离与恢复语义，而收益仅约 0.02–0.04 元/轮。在完成其余功能项之前，**不再把预算投入缓存优化**。

## 5. 验收方法

| 阶段 | 验证范围 | 预算（谷时） |
| --- | --- | --- |
| 阶段一 | 运维 + 开发 | ≈0.25 元 |
| 阶段二 | 运维 + 开发 | ≈0.25 元 |
| 阶段三 | 六领域完整验收 | ≈0.8–1.0 元 |

每次记录四个指标：**调用数、缓存命中率、实际扣费、评分**。任一项退化即回滚该阶段。

**质量门（不可放宽）**：六领域 `passed=true` 且评分不低于改动前（开发/运维/安全 100，跨域/资料/文档 95）。

## 5. 回滚与停止条件

- 每阶段独立提交，可单独回滚；
- 若命中率提升 < 3 个点，或调用数上升 > 20%，或任一评分下降，**停止后续阶段并回滚**；
- 若质量门出现功能性失败（测试/go vet 不通过），立即回滚阶段二，仅保留阶段一。

## 6. 时间与预算

- 总预算：约 **1.3 元**（谷时）；
- 执行窗口：18:00 之后；每阶段之间先看指标再决定是否继续。

## 7. 不做的部分

- 不做「整套工作流共用一个 Agent」——会破坏阶段职责与审批边界，与论文 2.2.4、3.4.2 的恢复语义冲突；
- 不关闭思考模式——实测会导致打转（开发 31→40 次、安全 251 次调用）；
- 不为缓存牺牲输出契约或质量门。
